# BJ v0.1.0 需求文档

## 1. 文档目的

本文档用于定义 `iroseclaw` 项目中 **Blackjack / 21点插件 v0.1.0** 的首版开发范围、运行环境、交互流程、依赖能力、约束条件与验收标准。

本版本聚焦于：

- 在 **蔷薇花园 IIROSE** 环境中运行
- 由 **机器人主持游戏流程**
- 支持 **房间内公开组织游戏**
- 支持 **通过私聊向玩家发手牌**
- 支持基本的 21 点结算流程
- 与当前 `iroseclaw` 的 **runtime plugin / tool / message handler 架构兼容**

本版本 **不追求赌场级复杂规则**，优先保证：

- 流程可跑通
- 状态清晰
- 机器人主持稳定
- 公屏 / 私聊边界明确
- 易于后续扩展到 v0.2.x / v1.0.0

---

## 2. 项目背景与现有架构结论

根据当前项目结构，`iroseclaw` 已具备如下基础：

1. **Koishi 插件式主入口**
   - 入口：`src/index.js`
   - 已存在 runtime plugin 注册体系
   - 已存在 games 插件：
     - `games-tictactoe`
     - `games-gomoku`
     - `games-number-guess`

2. **消息处理主链路已经存在**
   - `ctx.on('message', async (session) => { ... })`
   - 当前以“被提及触发”为主
   - 存在 runtime / legacy / hybrid 模式

3. **已有统一输出能力**
   - `OutputRuntime`
   - `sendToRoom()`
   - 已兼容：
     - 房间发言
     - 回复当前消息
     - 记录对话

4. **已有 IIROSE 相关能力插件**
   - `iirose-system-tools`
   - `iirose-user-profile-tools`
   - `iirose-room-tools`

5. **已有游戏类插件形态可参考**
   - 井字棋 / 五子棋 / 猜数字
   - BJ 插件应尽量对齐现有 `runtime/plugins/games/*` 风格

## 3. 目标插件定位

### 3.1 插件名称

建议：

- 插件内部名：`games-blackjack`
- 目录建议：`src/runtime/plugins/games/blackjack.js`
- 对外文档名：`Blackjack / 21点`
- 用户侧简称：`21点`、`BJ`

### 3.2 插件目标

让机器人在 IIROSE 房间中担任主持人，支持多人发起一局简化版 21 点，完成：

- 开局
- 报名加入
- 锁定玩家
- 私聊发牌
- 公开轮次控制
- 玩家选择操作
- 庄家行动
- 公开结算

### 3.3 版本边界

**v0.1.0 只做“可用 MVP”，不做以下内容：**

- 不做真实货币 / 蔷薇币结算
- 不做积分商城
- 不做保险（Insurance）
- 不做分牌（Split）
- 不做双倍下注（Double Down）
- 不做连续多桌并发复杂调度
- 不做跨房间共享牌局
- 不做 AI 玩家
- 不做图形 UI，仅文本流程

## 4. IIROSE + 机器人主持场景下的特殊需求

这是本插件与普通聊天机器人游戏相比最关键的部分。

### 4.1 公屏与私聊双通道协作

21点天然存在“暗牌/手牌私密信息”，而当前设想是：

- **公屏负责主持流程**
- **私聊负责发个人手牌与私人提示**

因此插件必须天然支持双通道：

#### 公屏职责
- 宣布开局
- 接收加入
- 宣布当前轮到谁
- 公布庄家明牌
- 公布玩家公共状态（停牌 / 爆牌 / 已完成）
- 公布结算结果

#### 私聊职责
- 给每位玩家发送自己的起手牌
- 在玩家每次要操作时，告知其当前手牌与点数
- 补牌后私聊发送最新手牌
- 必要时发送“你可回复：要牌 / 停牌”之类提示

### 4.2 主持型机器人而非自由聊天型机器人

本插件运行时，机器人不应像普通聊天一样自由发挥，而应表现为：

- 严格轮次推进
- 强状态机
- 明确主持口吻
- 尽量避免模型自由生成造成规则偏移

因此本插件核心逻辑应优先使用：

- **确定性代码逻辑**
- 而不是把规则判断交给 LLM

### 4.3 IIROSE 房间聊天噪声处理

蔷薇花园房间是实时聊天环境，存在大量无关消息，因此插件需要：

- 能在游戏进行中忽略无关聊天
- 仅识别与当前牌局相关的命令/短语
- 对非当前行动玩家输入进行约束
- 防止多人同时抢指令导致流程混乱

### 4.4 玩家可能不便频繁 @ 机器人

当前项目大多功能依赖“@提及触发”，但 21 点流程中如果每一步都要求 @ 机器人，会显得非常笨重。

因此 BJ 插件需要明确：

- **游戏内命令应支持低摩擦输入**
- 例如在已进入牌局的上下文中，允许识别：
  - 开局
  - 加入
  - 开牌
  - 要牌
  - 停牌
  - 结束
  - 取消
- 但同时要限制只在“当前房间有活跃 BJ 对局”时生效

这意味着插件很可能需要：

- 游戏态消息拦截
- 或专门的 trigger / direct tool 匹配支持

### 4.5 私聊限制与权限现实

当前 `src/index.js` 中有一条重要逻辑：

> 私聊硬编码权限：仅允许管理员 UID 触发机器人

这意味着如果 **直接复用当前通用私聊消息处理链路**，普通玩家在私聊里可能无法跟机器人正常互动。

因此在 BJ 插件开发时必须明确：

#### 结论 A
如果要实现“机器人私聊发牌 + 玩家通过私聊回复操作”，则必须调整现有私聊权限策略。

#### 结论 B
如果暂不调整私聊权限，则 v0.1.0 更稳妥的落地方式应为：

- **机器人通过私聊发牌**
- **玩家操作仍在房间公屏完成**

这是当前版本最符合现状的方案。

### 4.6 推荐的 v0.1.0 现实方案

结合现有架构，建议 v0.1.0 采用：

- 公屏开局 / 加入 / 开牌 / 行动 / 结算
- 私聊仅做：
  - 发起手牌
  - 发补牌结果
  - 发玩家个人状态提醒
- 玩家不依赖私聊回复
- 玩家在公屏输入：
  - `要牌`
  - `停牌`
- 机器人在公屏主持轮次，在私聊同步个人手牌

这既满足“私聊发牌”的核心目标，又绕开当前私聊权限约束。

## 5. 前置插件 / 前置能力 / 前置技能需求

本节专门回答“需要哪些前置插件、技能（如公屏聊天、私聊）”。

## 5.1 必要前置能力

### A. 公屏聊天发送能力（必须）
用途：
- 宣布开局
- 广播报名情况
- 公布轮到谁行动
- 宣布结算

依赖来源：
- `sendToRoom()`
- `OutputRuntime`
- Koishi `session.send()` / `bot.sendMessage()`

结论：**已具备，是必须依赖项。**

### B. 私聊发送能力（必须）
用途：
- 给玩家发送个人手牌
- 给玩家发送补牌结果
- 给玩家发送私人提醒

注意：
- 当前项目已具备消息发送框架，但是否能稳定向 IIROSE 指定用户私聊发送，需要结合适配器能力再确认实现细节
- 插件开发前应先验证：
  - 是否可按 UID 私聊用户
  - 私聊消息是否可靠到达
  - 私聊失败时如何降级到公屏提示

结论：**逻辑上必须，落地前需验证 IIROSE 适配能力。**

### C. 房间消息监听能力（必须）
用途：
- 接收“开局 / 加入 / 开牌 / 要牌 / 停牌”命令
- 判断是否来自当前牌局玩家

结论：**已具备。**

### D. 游戏状态存储能力（必须）
用途：
- 保存当前房间是否有对局
- 玩家列表
- 牌堆
- 手牌
- 当前轮次
- 庄家状态
- 超时状态

建议依赖：
- 参考现有 `data/games-*`
- 或 runtime state store / plugin 自有 state

结论：**必须具备，需要在 BJ 插件中实现。**

### E. 定时/超时能力（建议必须）
用途：
- 玩家长时间不操作时自动停牌 / 跳过 / 取消牌局
- 开局后报名倒计时

结论：**强烈建议纳入 v0.1.0。**

## 6.2 基础流程（建议最终采用）

## 阶段 1：开局

房间内有人发送：

`21点开局`

机器人公屏回复：

- 本局已创建
- 发起人是谁
- 多少秒内可加入
- 提示输入 `加入21点`

系统行为：
- 建立房间级 game session
- 状态=`waiting`
- 记录房主 / 发起人 / 玩家列表
- 默认发起人自动加入（建议）

## 阶段 2：加入

其他用户发送：

`加入21点`

机器人公屏回复：

- 玩家加入成功
- 当前人数
- 达到最小人数后可开始

约束：
- 同一用户不可重复加入
- 已开牌后不能加入
- 同房同一时刻只允许一局 v0.1.0 游戏

## 阶段 3：开始 / 锁定名单

满足最小人数后：

- 发起人发送 `开始21点`
- 或报名计时结束自动开始（可二选一，建议支持“手动优先，超时自动”）

机器人公屏回复：

- 报名结束
- 公布玩家名单
- 准备发牌

系统行为：
- 状态=`dealing`
- 洗牌
- 为每个玩家发两张牌
- 为庄家发两张牌（1 明 1 暗）

## 阶段 4：私聊发牌

机器人给每位玩家私聊：

- 你的手牌
- 当前点数
- A 的计分说明（若涉及）
- 提示后续在公屏输入 `要牌` / `停牌`

机器人公屏：

- 公布庄家明牌
- 公布当前轮到第一位玩家行动

## 阶段 5：玩家轮次行动

当前玩家可在公屏发送：
- `要牌`
- `停牌`

机器人处理：

### 要牌
- 为该玩家补一张牌
- 私聊该玩家新手牌与点数
- 公屏简报：
  - 某玩家要牌了
  - 当前状态：继续 / 爆牌 / 21点 / 已停牌

### 停牌
- 记录该玩家停止行动
- 公屏简报：
  - 某玩家已停牌
- 切换到下一位玩家

约束：
- 非当前行动玩家发送 `要牌/停牌` 时，机器人应提示“还没轮到你”
- 已爆牌/已停牌玩家不能再次操作

## 阶段 6：庄家开牌与行动

所有玩家都完成后：

机器人公屏：
- 公布庄家暗牌
- 根据规则补牌

建议规则：
- 庄家点数 < 17：必须要牌
- 庄家点数 >= 17：停牌

机器人逐步公屏播报庄家补牌过程。

## 阶段 7：结算

机器人公屏输出：
- 每位玩家最终点数
- 庄家最终点数
- 每位玩家结果：
  - 胜
  - 负
  - 平局
  - 爆牌失败
  - Blackjack

系统行为：
- 状态=`settled`
- 写入游戏结果日志
- 清理房间局状态

## 7. 推荐状态机设计

建议最小状态机：

- `idle`：无对局
- `waiting`：已开局，等待加入
- `dealing`：发牌中
- `player_turn`：玩家轮次中
- `dealer_turn`：庄家轮次
- `settled`：已结算
- `cancelled`：已取消

### 玩家子状态
- `joined`
- `active`
- `stood`
- `busted`
- `blackjack`
- `done`

## 8. 规则定义（v0.1.0）

## 8.1 牌组
- 使用标准 52 张牌
- 不区分花色功能，仅保留展示
- 每局重新洗牌

## 8.2 点数
- 2~10 按面值
- J / Q / K = 10
- A = 1 或 11，取对玩家最优但不爆的值

## 8.3 Blackjack 判定
- 起手两张合计 21，记为 Blackjack
- Blackjack 应高于普通 21 点

## 8.4 庄家规则
- 小于 17 必补
- 大于等于 17 停牌

## 8.5 输赢判定
- 玩家爆牌：直接输
- 庄家爆牌：所有未爆牌玩家赢
- 双方都未爆：比较点数
- 相同点数：平局
- 玩家 Blackjack 对普通 21：玩家胜

## 9. 文案与展示要求

## 9.1 公屏文案要求
- 简短
- 主持风格明确
- 一次只说当前推进所需信息
- 避免把所有私人牌面都公开

### 示例
- `21点已开局，30秒内可发送“加入21点”报名。`
- `当前玩家：Alice，请发送“要牌”或“停牌”。`
- `Bob 选择要牌，结果已私聊发送。`
- `庄家明牌：K。`
- `本局结束，开始结算。`

## 9.2 私聊文案要求
- 明确显示手牌
- 明确显示点数
- 明确下一步提示

### 示例
- `你的起手牌：A♠、9♥，当前点数 20。请在公屏等待轮到你时输入“要牌”或“停牌”。`
- `你抽到：5♦。当前手牌：A♠、9♥、5♦，当前点数 15。`

## 10. 异常与边界情况

### 10.1 只有 1 人开局
- 是否允许单人对庄家？
- 建议：**允许**，简化流程

### 10.2 玩家中途离开房间
- v0.1.0 建议：
  - 若已开局且玩家离线/离房，不做复杂监听
  - 超时未操作则自动停牌或判弃权

### 10.3 私聊发送失败
- 必须有降级方案：
  - 公屏提醒该玩家“私聊发送失败，请检查私聊是否可用”
  - 或临时改为 `@用户 你的手牌发送失败，请联系管理员` 
- 不能因为单个私聊失败导致整个牌局崩溃

### 10.4 多人同时发操作指令
- 只接受当前行动玩家指令
- 其他人输入忽略或提示

### 10.5 机器人重启 / 插件异常
- v0.1.0 可接受重启即丢局
- 但应在文档中注明：
  - **不要求断点恢复**

### 10.6 恶意刷屏
- 应限制：
  - 非游戏命令不推进状态
  - 同一玩家高频重复 `要牌` 不应多次生效

## 13. 与现有项目的适配要求

## 13.1 消息触发要求

当前项目主要依赖 `@机器人` 触发；BJ 插件需要在“游戏进行中”支持无 @ 的简短命令。

因此需要新增或扩展一种机制：

- 当房间存在活跃 BJ 对局时
- 对该房间消息进行额外匹配
- 识别游戏命令并优先交给 BJ 插件处理

## 13.2 私聊权限要求

当前系统对私聊有“仅管理员”限制。

### v0.1.0 要求
- **不要求玩家通过私聊操作**
- 但要求机器人能尝试向玩家私聊发消息

### 后续版本需求
- 若要支持“玩家私聊回复 要牌 / 停牌”，则必须：
  - 为游戏临时会话放宽私聊权限
  - 或专门新增游戏私聊白名单机制

- 开局人
- 玩家列表
- 每次发牌
- 每次要牌/停牌
- 最终结算
- 异常中断原因

建议输出到：
- `logs/bot.log`

## 16. 推荐的 v0.1.0 最终流程架构（结论版）

基于当前项目实际情况，建议采用以下最终方案：

### 流程摘要
1. 玩家在房间发送 `21点开局`
2. 机器人公屏宣布开局并开启报名
3. 玩家发送 `加入21点`
4. 发起人或倒计时结束后 `开始21点`
5. 机器人私聊给每位玩家发送起手牌
6. 机器人公屏公布庄家明牌与当前行动玩家
7. 玩家在公屏输入 `要牌` / `停牌`
8. 每次补牌结果私聊玩家，同时公屏简报
9. 所有玩家结束后，庄家自动行动
10. 机器人公屏统一结算并结束本局

### 该方案的优点
- 符合“机器人主持”
- 符合“私聊发牌”
- 不依赖放开普通玩家私聊权限
- 与当前项目架构兼容性最高
- 后续可平滑升级为：
  - 私聊回复操作
  - 积分下注
  - 分牌 / 双倍
  - 多桌管理

## 18. 结语

BJ v0.1.0 的核心不是“做一个最全的 21 点”，而是：

> **在 IIROSE 的房间公屏 + 私聊混合环境中，让机器人稳定地主持一局 21 点。**

因此开发重点必须放在：

- 状态机
- 公私聊边界
- 当前玩家约束
- 私聊失败降级
- 现有 iroseclaw 架构兼容性

而不是过早追求高级玩法。
